# 即時行情四組策略比較：Gemini 實作計畫

## 1. 目標與範圍

在「即時行情儀表板 → 自動交易」頁面建立四組合約紙上交易比較，研究原有跟進規則、LightGBM 排名與語言模型過濾的差異。

| 組別 | 即時跟進規則 | LightGBM 排名過濾 | 語言模型過濾 | 語言模型解讀 |
|---|---:|---:|---:|---:|
| A：規則基準 | ✓ | — | — | ✓ |
| B：規則＋AI | ✓ | — | ✓ | ✓ |
| C：規則＋LightGBM | ✓ | ✓ | — | ✓ |
| D：LightGBM＋AI | ✓ | ✓ | ✓ | ✓ |

第一版僅支援 **Futures 模擬交易**。四組必須各自維護獨立本金、委託、持倉與績效；不送出真實訂單。

目前專案已有未提交修改，包含 Collector 記憶體及模型前向測試修補。實作前先檢查 `git status` 與差異，保留這些修改，禁止以重置或覆蓋方式清除。

## 2. 現有架構與沿用方式

- 即時訊號由 `useMarketAlerts` 產生 `MarketTradeFrame`，經 `useAutoTrading` 分派給 `AutoTradingEngine` 及現有 `ABComparisonCoordinator`。
- 現有 A/B 協調器提供兩組獨立引擎、AI 分析版本檢查、批次租約與紀錄，可作為四組協調器的參考。**保留舊版批次語意與讀取方式**，新增四組批次類型與版本，不把舊 A/B 紀錄解讀成四組。
- 既有 LightGBM 使用研究幣種池與已收盤小時資料，輸出多空排名；目前自動滾動流程同時依賴 Chronos-2，需拆出可獨立完成的 LightGBM 排名流程。
- 現有 AI 供應介面是 `AnalysisProvider`。新增 Ollama 供應方式時沿用資料快照驗證、輸出驗證與期限檢查，保留原有供應方式的隔離驗證，不能用 Ollama 的連線成功狀態取代其他供應器的驗證結果。

## 3. 四組交易與資料流程

### 3.1 共同輸入

批次建立時固定：

- Futures 市場、追蹤幣種清單、起始本金、風險與成交參數。
- LightGBM 排名規則、研究幣種池與排名版本政策。
- Ollama 供應器位址、模型名稱、提示版本與 AI 過濾規則版本。

追蹤幣種沿用現有上限 **10 個**，且必須屬於 LightGBM 固定研究幣種池；批次建立前顯示不符合的幣種並拒絕啟動。LightGBM 仍對**完整研究幣種池**排序，再用排名評估使用者選取的追蹤幣種，避免只對少數追蹤幣重新排序。

同一筆 `MarketTradeFrame` 與同一個已確認的跟進計畫必須送入四組。每組沿用 `AutoTradingEngine` 的交易與風控規則，包括：

- 預設本金 10,000 USDT、單筆風險預算 0.5%、名目金額上限 20%、最多三個持倉。
- 現有訊號確認、250 毫秒模擬延遲、入場逾時、停損、分批停利、15 分鐘持倉期限、滑價、手續費及資金費規則。
- 各組獨立執行現金、持倉數及交易所規格檢查；某組被拒絕不影響其他組。

### 3.2 LightGBM 排名門檻

收到跟進確認訊號時：

- LONG 必須是最新有效多頭排名前 3 名。
- SHORT 必須是最新有效空頭排名前 3 名。
- 同時出現在多空衝突清單的幣種拒絕進場。
- 只採用訊號確認時間之前已完成、且對應當時**最新已收盤小時**的排名快照；不得等待稍後完成的排名補作過去決策。
- 缺少排名、排名過期、幣種資料不足或模型未就緒時，C、D 組略過該訊號並記錄原因；A、B 組繼續執行。

每個決策保存排名快照 ID、資料截止時間、發布時間、模型版本與雜湊、幣種排名、方向與判定原因。

### 3.3 語言模型過濾

同一訊號的四組共用同一份 AI 分析快照：

- 提供四組相同的行情摘要、分析方向、理由、風險與資料缺漏。
- A、C 組只顯示與記錄解讀；B、D 組額外執行過濾。
- B、D 僅在分析於訊號確認前已可取得、未過期、必要資料完整、模型及提示版本與批次設定相符，且分析方向與訊號方向一致時允許進場。
- 分析不可用、過期、中立、方向不符、格式錯誤或資料不足時，B、D 拒絕進場並記錄明確原因。不得等待事後生成的分析補判。
- AI 分析沿用目前快照有效期與驗證規則；模型輸出必須通過既有結構驗證，無效輸出不得直接轉成交易決策。

四組均須記錄同一訊號 ID、確認時間、AI 快照 ID、快照時間、模型名稱、方向、過濾結果與原因，即使某組不使用 AI 作為進場條件。

## 4. LightGBM 與其他模型的訓練

### 4.1 獨立 LightGBM 更新

將每小時流程拆分為：

1. 同步研究幣種池的已收盤 1 小時 K 線與資金費資料。
2. 沿用目前 **180 天滑動視窗**、訓練／驗證切分與資料完整性檢查。
3. 重訓 LightGBM 多頭及空頭排名模型。
4. 驗證結果後原子發布模型與排名快照。
5. 排名與版本供四組比較讀取，整個流程不啟動或等待 Chronos-2。

排程預設每小時一次；相同截止時間不得重複訓練。若更新失敗，記錄錯誤並保留先前產物作追溯，但不得將舊排名當成目前小時的有效排名。

記錄每次訓練的開始／結束時間、CPU 與記憶體觀測值、資料截止時間、成功或失敗，以及排名發布時間。第一版不自動縮短重訓週期，待實測資源與資料時間尺度後再決定。

### 4.2 暫停其他模型訓練

- 停止 Chronos-2 及其他既有 AI 模型的背景自動訓練排程。
- 停用或拒絕相應的手動訓練 API 與 UI 入口，回傳可理解的「目前暫停」訊息。
- 不刪除既有權重、研究資料、歷史批次、模型前向測試紀錄與輸出。
- LightGBM 是使用者明確保留的例外，維持每小時訓練與排名。

若舊模型前向測試仍在運行，使用既有停止流程：取消待入場單，對持倉提出模擬出場，等待後續合格成交；行情不可用時顯示「停止中」及原因，不虛構平倉。舊實驗停止與四組批次的啟動狀態必須清楚顯示。

## 5. Ollama 串接

- 新增 Ollama 供應器，預設連線 `http://127.0.0.1:11434`；提供可設定的遠端服務位址，模型名稱由目標服務實際列出的模型選取。
- 本機先使用可取得的 **Gemma 4 E2B** 版本測試。不得假定本機已安裝 Ollama 或已下載特定模型；啟動前顯示服務、模型與測試連線狀態。
- 批次開始後鎖定服務位址、模型與提示版本；修改設定只影響新批次。
- 使用既有 `AIDataSnapshot` 與 `AIAnalysisResult` 的結構和驗證流程；明確區分 Ollama 連線／模型可用性與其他 CLI 供應器的隔離驗證。
- 設定請求逾時與取消；避免同一幣種重複排入無上限請求。逾時或無效輸出時不阻塞交易串流，AI 過濾組依不可用處理。
- 連接遠端 Ollama 前，介面顯示將傳送的行情摘要範圍；不要在批次紀錄或日誌中保存密碼、權杖或其他憑證。

## 6. 介面、API 與紀錄

### 6.1 頁面

在現有自動交易頁面增加四組比較模式：

- 啟動區顯示 Futures、追蹤幣種、共同風控參數、LightGBM 最新版本與資料截止時間、Ollama 狀態及模型。
- 四張並列帳戶卡顯示淨值、報酬、已實現／未實現損益、手續費、資金費、最大回撤、交易筆數、勝率與未完成狀態。
- 訊號明細顯示每組是否允許、實際是否成交、排名條件、AI 判定及拒絕原因。
- 顯示 AI 可用覆蓋率、LightGBM 排名可用率、過濾數量、被擋訊號在對照組中的實際結果。
- 暫停、繼續、停止新進場及模擬平倉操作同步作用於四組，且顯示各組完成狀態。
- 保留舊單組與 A/B 歷史頁面的讀取與原本標示。

### 6.2 介面與儲存

新增四組批次資料版本，包含：

- 批次設定、建立時間、狀態、版本、四個帳戶快照及批次共同的資料來源設定。
- 每個訊號的四組判斷、排名與 AI 快照參考、時間戳、通過／拒絕原因。
- 按組彙總的績效與資料完整性狀態。

新增或擴充 Collector API，以提供：

- Ollama 服務狀態、可用模型及連線測試。
- LightGBM 最新排名快照、模型版本、資料截止時間及更新狀態。
- 四組批次的建立、讀取、儲存、租約與匯出。

新批次維持現有 owner lease、revision 檢查與原子保存原則。採用獨立批次類型／儲存紀錄，避免修改舊版 A/B payload 的語意；舊紀錄保持可讀，無需搬移。

## 7. 測試與驗收

### 策略與時間順序

- 同一訊號分別測試：排名與 AI 均通過、僅排名失敗、僅 AI 失敗、兩者均失敗。
- 測試多空前 3 名、衝突幣、未涵蓋幣、排名未就緒、舊排名及跨整點時效。
- 測試 AI 分析未到達、事後到達、過期、中立、方向不符、缺資料、版本不符及格式錯誤。
- 驗證四組使用同一行情事件及當時已可取得的快照；各組資金與持倉獨立。

### 運行與相容性

- 測試 LightGBM 獨立更新成功、失敗及同小時去重，確認不觸發 Chronos 訓練。
- 測試 Ollama 本機及模擬遠端服務的連線、模型列表、逾時、斷線、重新連線與批次設定鎖定。
- 測試四組批次租約、revision 衝突、儲存失敗、中斷恢復及匯出。
- 測試舊 A/B 歷史紀錄仍可讀；測試舊模型前向實驗停止、等待模擬平倉及無行情時的狀態。
- 驗證其他模型的自動與手動訓練入口均已暫停，既有模型與紀錄仍在。

### 最終驗收

- 執行相關核心、Collector 與前端測試，完成建置和靜態檢查。
- 在頁面確認四組卡片、訊號原因、模型狀態、舊歷史批次及匯出內容。
- 使用測試資料執行完整紙上流程，確認所有進場、出場與 AI 判斷均可追溯。
- 回報本機 Gemma 實際模型名稱、推論耗時、記憶體使用與測試限制；未完成長時間即時測試時，不宣稱長時間穩定或策略獲利。
